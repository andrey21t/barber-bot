## FSM (aiogram 3.x)

### FSM timeout — точка отсчёта

**Правило:** FSM timeout = время от **последнего** сообщения пользователя, НЕ от старта сессии.

**Почему:** каждый message обновляет `last_message_at` в `state.update_data()` → таймер продлевается. Это как банковская сессия — активность = продление.

**Паттерн (middleware):**
```python
state_data = await state.get_data()
last_at = state_data.get("last_message_at")
if last_at:
    elapsed = (datetime.utcnow() - last_at).total_seconds()
    if elapsed > SESSION_TTL_SEC:
        await state.clear()  # ДО event.answer (race condition)
        return await event.answer("⏰ Сессия истекла...")
await state.update_data(last_message_at=datetime.utcnow())  # продлеваем
return await handler(event, data)
```

**Грабли (где ошибся 2026-07-19):**
- Думал что timeout от **старта** сессии → неверно
- Думал что `state.clear()` "очищает счётчик для нового отчёта" → неверно, он сбрасывает FSM в idle
- Думал что `update_data` "стартует новую сессию с начала" → неверно, он продлевает текущую

**Insight:** если юзер писал "Иван" T=0, молчал 35 мин, написал "петров" T=35 →
- `elapsed = 35*60 = 2100 сек > 1800` ✅
- `state.clear()` → state = State(None), "Иван" потерян
- `event.answer("⏰ Сессия истекла")` → юзер видит сообщение
- `return` → "петров" НЕ сохраняется, handler не вызывается
- Юзер должен `/book` заново.

## Spec-driven development

### Структура spec.md — не пихать блоки куда попало

**Правило:** новые разделы вставлять **отдельным блоком** с `---` разделителем, не вклинивать в чужой раздел.

**Грабли (2026-07-19):** вставил 3 gap-блока (`/cancel` в FSM, FSM-таймаут, FSM-storage) прямо посреди раздела `/cancel` для клиента → `### FSM таймаут` оказался между Rate limit и Deploy, `## Gap 3` (мой текст-подсказка) попал в файл как заголовок.

**Паттерн:** все дополнения в spec → в конец файла или в новый раздел `## FSM edge cases` с `---` разделителями между блоками.

## Формат работы (dev-режим, не педагогика Уровень 2)

**Контекст:** после woodworking (TypeScript/Vite, 513 тестов, Three.js, PDF) — база программирования уже есть.
Педагогика «объясни обратно / скелет в псевдокоде / прогрессивная сложность» (скилл `autotest-mentor` Уровень 2) — тормозит.
Дальше работаем как dev-задача: deep-analysis на нетривиальное → реализация → verify → code-review.

**Резюме после каждого блока (8-15 строк):**
1. **Что сделали** — какие файлы правили, какие команды добавили (что, не как).
2. **Зачем это продукту** — какую боль закрывает для пользователя (Екатерина-мастер / клиент).
3. **Базовая вещь для понимания** (если есть) — паттерн/подход в 1-2 строках, без deep-тех. деталей.
   Пример: «Timezone invariant: slot.slot_hour — ЛОКАЛЬНЫЙ час, в DB храним UTC. Не путать — иначе записи съедут на 3 часа.»
4. **Что НЕ сделали (отложено)** — если что-то явно выпало в TODO, упомянуть.

**Гейты (как в AGENTS.md, кратко):**
- Deep-analysis на нетривиальное (handlers/master.py с APScheduler — нетривиально, парсинг команд — trivial).
- Verify-and-fix перед «готово»: pytest, ruff, mypy — все зелёные.
- Code-review на logic-change (новая фича, багфикс с logic) — через `code-reviewer` subagent.
- Pre-push ревью в playtest здесь НЕ нужно — это личный репо, коммит свободный (AGENTS.md § git-repo-categories).
- Коммитить свободно, без переспроса (pet-проект).

**Anti-паттерн (что НЕ делаем):**
- ❌ Не выдаю готовый код без объяснения «зачем»
- ❌ Не прошу «объясни обратно» (это Уровень 2, не наш уровень)
- ❌ Не пишу скелеты в псевдокоде — пишу реальный код
- ✅ Объясняю паттерны/инсайты в резюме, не в самом коде (код = чистый, резюме = контекст)
